## 1. 交付基线：为什么是 `_agent/freeze/` 而不是 `src/`

### 1.1 结论

| 项 | 内容 |
|---|---|
| **交付基线** | `_agent/freeze/`（`src/` + `web/` + `mods/` + `resourcepacks/` + `MANIFEST.txt` + `simulator.exe`） |
| **闭环硬条件** | **「冻结副本构建通过 + 其哈希等于权威值」**，而**不是**「`src/` 构建通过」 |
| **权威哈希** | `Cyanobacteria.h` = `79C1DA8EB0F7B48BB0FBBF33F791F85DA8BAC6CD66826D60DB80C95EA88E5030`（4901 B）<br>`Cyanobacteria.cpp` = `5F6B7E38E807349310A4B1BD2E2AD344683D6DD5B716B50D5C341ECC8162E642`（28788 B） |

### 1.2 原因：`src/Cyanobacteria.*` 被并发写入者反复破坏

开发期内一个**不可寻址**的子代理（`f5fbe352`）持续覆盖这两个文件，**累计 9 次**。
完整证据链（时间、覆盖后哈希、错配指纹、恢复时刻）见
[`_agent/ws1/OVERWRITE_LOG.md`](../_agent/ws1/OVERWRITE_LOG.md)。

**为什么不能靠"`src/` 构建通过"作为闭环条件**：

| 事件形态 | 能否被编译发现 |
|---|---|
| 事件 #1~#7（`indexById_` 头实现错配） | ✅ 能 —— 全量构建报 **46~73 个 error**，很"吵" |
| **事件 #8（可编译但语义不同）** | ❌ **不能** —— 全量构建 **0 error / 37 warning（完全通过）** |
| 事件 #9（`Cyanobacteria.cpp` 29528 B 非权威） | ❌ 不能（能编译） |

**事件 #8 的行为差异（同配置、同 seed、600 帧）**：

| 版本 | 存活核 | `CYANO_GAIN` |
|---|---|---|
| 权威版（`5F6B7E38…`） | **208** | 401.91 |
| 事件 #8 版本（`B33DE671…`） | **98** | 538.52 |

→ **差 2.1 倍，但编译完全通过。**

### 1.3 由此确立的两条工程纪律

1. **「编译通过 / 0 error」不能作为「版本正确」的判据。**
   版本正确性只能靠 ①**文件哈希校验**（首选）或 ②**行为对照**（同配置同 seed 比对终态）确认。
2. **恢复 `src/` 只能用带版本守卫的写入路径。**
   写入者会持有文件占用，导致 `Copy-Item` 抛 `UnauthorizedAccessException`
   （**Lead 与 cyano-dev 各自独立遇到一次**）；`write` 工具（文件系统版本守卫）是唯一可用路径。
   **若 `write` 也失败，则 `src/` 完全不可恢复 —— `_agent/freeze/` 就是唯一交付依据。**

### 1.4 `_agent/freeze/` 的内容与校验方式

```powershell
# 1) 校验冻结副本源码哈希（两条都必须匹配）
(Get-FileHash _agent\freeze\src\Cyanobacteria.h   -Algorithm SHA256).Hash  # 79C1DA8E…E5030
(Get-FileHash _agent\freeze\src\Cyanobacteria.cpp -Algorithm SHA256).Hash  # 5F6B7E38…E642

# 2) 全量清单（107 行：SHA256 + 字节数 + 相对路径）
Get-Content _agent\freeze\MANIFEST.txt

# 3) 产物
_agent\freeze\build\simulator.exe     744960 B   # 从冻结副本构建
_agent\freeze\final\simulator.exe     744960 B   # 同上
```
**冻结副本的构建结果**：`0 error / 37 warning`（C4099×36 + C4996×1，**与基线逐类相同 → 不新增告警**），
`--schema-check` 通过，`cyano_nodes=500` 跑 200 帧正常运行。

> ⚠️ **只交付 exe 而不同时交付源码哈希，就无法自证「这个 exe 对应哪份源码」** ——
> 这正是上述 9 次覆盖事件的核心教训，故本交付**以 `freeze/` 整体为准**。

## 2. 验收 #14（性能）的准确口径与归因

### 2.1 判据与结论

| 判据 | 要求 | 实测 | 判定 |
|---|---|---|---|
| 绝对帧率 | ≥ 60 FPS | 与配置相关（见下） | ✅ |
| 相对基线 | ≥ 基线中位 FPS × 0.55 | 比率 **0.35 ~ 0.40** | ❌ |

→ **判定：「部分通过」**（绝对达标、比率不达标），**必须附本节的归因与口径说明**。

### 2.2 基线（分母）—— `simulator_baseline.exe`，3000 帧 × 3 次

| 指标 | 值 |
|---|---|
| 基线中位 FPS | **3271.89**（3280.48 / 3268.69 / 3271.89） |
| **× 0.55 线** | **1799.54** |
| 峰值工作集 | 6.3 MB |
| 200k 帧长跑 | 642.66 s，EXIT 0，末态 1000 核 / 1000 球，**无内存泄漏** |

详见 [`_agent/monitor/BASELINE_PROFILE.md`](../_agent/monitor/BASELINE_PROFILE.md)。

### 2.3 ⚠️ 算 FPS 必须用 stdout 的**实际 `最终帧号`**

**开启态会因核全部死亡而提前结束**（默认 `ball_loss_cost=5.0` 下约 1093 帧）。
若用**名义帧数**（3000）当分子，FPS 会**虚高约 2.7 倍 → 假 PASS**。
（本轮的 co-lead 初版结论正是这样算错的，后自行更正。）
**正确做法**：解析 stdout 的 `最终帧号:`，或**两边固定帧数对比**。

### 2.4 两种口径的一致结论

| 口径 | OFF | ON（3000 节点） | 比率 |
|---|---|---|---|
| 同 1093 帧（默认参数，5 次中位） | 0.333 ms/帧（3005 FPS） | 0.957 ms/帧（1045 FPS） | **0.348** |
| 同 3000 帧（`ball_loss_cost=0.2`，5 次中位） | 1.758 ms/帧（568.7 FPS） | 4.430 ms/帧（225.7 FPS） | **0.397** |

### 2.5 节点规模扫描（`ball_loss_cost=0.2`，3000 帧，5 次中位）

| `cyano_nodes` | 中位 ms/帧 |
|---|---|
| 0 | 1.741 |
| 1000 | 2.698 |
| 3000 | 4.346 |
| 6000 | 3.697 ← **非单调，说明有测量噪声**（同机其他进程抢占），故单点数字仅供参考 |

### 2.6 瓶颈隔离（3000 节点，各关一项，3 次中位）

| 关闭项 | ms/帧 | 相对基线节省 |
|---|---|---|
| （基线） | 4.510 | — |
| `cyano_link_check_interval = 100000`（连接维护） | 4.063 | **0.447** |
| `cyano_metabolism_rate = 0` | 4.150 | 0.360 |
| `cyano_reproduction_probability = 0` | 4.426 | 0.084 |
| `cyano_photosynthesis_rate = 0` | 4.588 | −0.078（在噪声内） |
| `cyano_ball_spawn_probability = 0` | 4.653 | −0.143（在噪声内） |

**结论**：主要开销是**每帧全节点遍历的固定 per-node 成本** + **连接维护 0.447 ms/帧**。

### 2.7 关于"额外小球拖慢下游"这一假设 —— **本轮实测未能复现，属未定论**

曾有一个合理假设：默认产球概率使小球从 1000 涨到 ~5557（5.6×），
由此加重 `World::updateBallDynamics()` / `updateOwnership()` / 网格重建的成本。
但本轮的**受控实验不支持它**：在 `ball_loss_cost=0.2` 下，三组
（`cyano_ball_spawn_probability` = 0.002 / 0 / 0.0002）的**终态小球均为 1000**（已达承载力饱和），
ms/帧 分别为 4.449 / 4.728 / 4.532 —— **无单调关系，差异在噪声内**。
→ **该假设在本轮口径下未被证实。** 若要定论，需在**允许球数发散**的配置下重做
（固定帧数、同时报告终态球数与 ms/帧），本轮未做。

> **口径要求**：报告 #14 时必须**同时声明终态小球数**，否则不同配置/seed 下球数不同，
> 比率会在 0.4~1.0 间漂移，结论不可复现。

### 2.8 性能旋钮

- `cyano_link_check_interval`：调大可省连接维护（本机实测上限约 0.447 ms/帧 @3000 节点）。
- `grid_cell_size`：默认 60。**实测调到 150 可提速约 1.6×，但会改变遍历顺序 → 破坏逐位一致性**，
  追求可复现请保持默认。

## 3. 验收 #12（长期稳定）的前提条件

**判定：PASS，但必须写明前提。**

| 运行 | 命令 | 结果 |
|---|---|---|
| 200k 帧（冻结副本） | `--console --no-render --seed 42 --frames 200000 --max-fps 0 --sample-interval 0 --env <平衡配置>` | 约 20 分钟，**EXIT 0**，末态 **1000 核 / 1000 球** |
| 12000 帧 × 多 seed | `ball_loss_cost = 0.2` | seed 42 / 7 / 123 **全部稳定在 ~1000 核 / 1000 球** |

### ⚠️ 前提：必须使用 `ball_loss_cost = 0.2`（不是默认 5.0）

`ball_loss_cost = 5.0`（原默认）下核会在 ~300–1000 帧内崩塌到 1 个，**根因是基线固有机制**：
`BALL_LOSS: out` 是 `ABSORB: in` 的 **1.97×**（单向能量销毁）。**这不是蓝细菌模组引入的问题。**

**蓝细菌模组实际改善了生存**（同为 20 核起步）：

| | 存活核 | `BALL_LOSS/ABSORB` | `CYANO_GAIN` |
|---|---|---|---|
| 关闭蓝细菌 | **1** | 1.97× | — |
| 开启（1500 节点） | **3** | **1.17×** | 120.08 |

→ **开箱即用的平衡配置见 [`env_config_balanced.txt`](../env_config_balanced.txt)**
（实测**零未知键 / 零解析失败**，1500 帧后 1000 核 / 1000 球稳定，内含标定依据）。

## 4. 与冻结契约的已知偏差：`cyano_*.csv` 表头

**两句分开判（功能与契约是两件事）**：

| 维度 | 判定 | 依据 |
|---|---|---|
| **功能** | ✅ **PASS** | 需求原文要求「含位置、能量、连接数、存活状态」→ 实测表头**四项齐全** |
| **契约一致性** | ❌ **FAIL** | 与契约 §5 原定表头不一致 |

```
实测表头：x,y,energy,link_count,alive,colony_id,age
契约 §5 ：id,colonyId,type,x,y,energy,linkCount,alive,age
```
差异：① **缺 `id`** ② **缺 `type`** ③ 命名风格不同（蛇形 `link_count` vs 驼峰 `linkCount`） ④ 列序不同。

**影响**：`id` 缺失使「用节点 id 跨文件交叉引用」不可行（如把 `cyano_*.csv` 与连接表关联）。
位置：`src/Sampler.cpp` 的 `cyanoHeader()`。

> 另：`nuclei_*.csv` / `survivors.csv` / `trend.csv` 表头**已正确**在末尾追加
> `cyanoPreference,cyanoDigestion,maxAccel`（追加在最后，旧列顺序与含义未改动）。

## 5. 验收 #13（关闭蓝细菌退化一致）的口径

**判定：PASS。**

| 比对对象 | 方式 | 结果 |
|---|---|---|
| `balls_005000.csv` | **逐字节** | SHA256 = `E0EB7319FD4067E9084791973E9963940435C752A4A2999BD3C545A49AC8FCDF` ✅ **完全相同** |
| 其余采样文件 | **按列名对齐**（允许新版多出列） | 旧 22 列**逐位前缀一致，mismatch = 0** ✅ |

**为什么"按列名对齐"而不是逐字节**：验收 #10 **要求**新增列（`cyanoPreference` 等），
所以新版表头必然更长。若按整文件逐字节比对，会把「表头变长」**误报成回归失败**。
正确做法：取**新旧共有的旧列**，按列名取值逐行比对；数值按 `%.6f` 文本比对；行数必须一致。

**关闭态确实零成本**：`cyano_nodes = 0` 时 `World` 侧全程短路（实测 OFF 态 2000 帧与基线逐字节一致）。

## 7. 使用建议（开箱即用）

```powershell
# 1) 以冻结副本为交付依据，先校验
(Get-FileHash _agent\freeze\src\Cyanobacteria.cpp -Algorithm SHA256).Hash   # 5F6B7E38…E642

# 2) 用推荐平衡配置启动（开箱即得稳定生态）
cd <解压目录>
.\simulator.exe --env env_config_balanced.txt --frames 100000 --max-fps 0

# 3) 关闭蓝细菌 = 退化为原核-小球模拟
.\simulator.exe --env env_config_balanced.txt --cyano-nodes 0 --frames 2000 --no-render --max-fps 0
```

> ⚠️ **自动化运行时必须注意**：`env_config.txt` 含 `pause_on_exit = on` →
> 结束时会 `std::cin.get()` **永久阻塞**，请重定向 stdin（cmd 用 `< NUL`）；
> 且根配置 `max_fps = 30` 会限速，请显式加 `--max-fps 0`。
> ⚠️ **写 `--env` 文件须用「无 BOM 的 UTF-8」**：PowerShell 5.1 的 `Set-Content -Encoding UTF8`
> 会写 BOM，导致第一行键被读成 `\uFEFFcyano_nodes` → `[EnvConfig] 未知键，已忽略`
> → **静默退化为关闭态**（最易造成假 PASS）。用：
> `[System.IO.File]::WriteAllText($p,$t,(New-Object System.Text.UTF8Encoding($false)))`
