# 长线任务工作流手册（可复用）

> **2026-10-31 增补**：本手册的"可直接复制版"已独立成文 —— 见 [PLAYBOOK.md](PLAYBOOK.md)，
> 含主代理系统提示、心跳提示词、5 种角色卡全文、13 条反模式清单。
> 本文件保留完整叙事与血泪案例（为什么每条规则长这样）。

> 从一次 13 小时夜班（791 分钟 / 55 个子代理 / 39 次成功）中沉淀。
> 本文的目标是：**换到别的项目，照着做就能高效跑长线任务**。
>
> 硬数据（来自会话事件日志，非印象）：
> - 会话跨度 791 min，其中 **677 min（85%）是我的 sleep 轮询**，不是实际工作
> - 子代理 55 个：成功 39 / 失败 7 / 悬挂被杀 9（悬挂平均干等 24 min 才发现）
> - 理论容量约 160 个代理，实际完成 39 个 → **利用率 24%**
>
> 结论：**不是模型慢，是把并行做成了串行，又把等待做成了睡眠。**

## 第 0 部分：三条铁律

### 铁律 1：绝不阻塞等待

```
❌ 派活 → sleep 300s → 看一眼 → sleep 300s → ...
✅ 派活 → 立刻做下一件独立的事 → 只在真无事可做时才等
```

**为什么**：sleep 期间机器完全空转，0 产出。这次 85% 的时间浪费在这里。

**怎么做**：
- 单次等待不超过 **120 秒**
- 连续 3 次等待视为该代理已死，立即 `interrupt_agent`
- 等待时优先做：写契约、跑门禁、读别人的代码、更新文档

### 铁律 2：把并发槽位打满

先确认**允许的并发上限**（模型/账号/额度），然后**始终打满**。

本次是 2 账号 × 2 并发 = 4 槽，但实际长期只有 1 个在跑。

切分原则：**按目录独占**，不是按功能。

| 槽位 | 职责 | 典型产出 |
| --- | --- | --- |
| A | 实现（独占 src/module1） | 代码 |
| B | 实现（独占 src/module2） | 代码 |
| C | 测试/实验（独占 tests/ 或 experiments/） | 单测、数据 |
| D | 审查或文档（只读 + 独占 docs/） | 缺陷清单、文档 |

### 铁律 3：任务切片以"8 分钟"为单位

本次平均 **23.9 次工具调用/代理**，20 个代理超过 15 分钟。中途一出错整段作废。

**切片标准**：
- 一个代理**最多碰 3 个文件**
- 一个代理**最多跑 3 条验收命令**
- **必须能在 8 分钟内完成**；做不到就再切
- 切分维度：按文件、按测试、按命令 —— **不按"功能"**

## 第 1 部分：子代理契约模板

这是实践中效果最好的结构。**每一条都不能省**，省哪条就踩哪个坑。

### 1.1 通用模板

```markdown
你是 <项目名> 的 <角色>。项目根：<绝对路径>

## 你独占的路径
<文件或目录清单，逐个列出>
**禁止**：<明确列出不许碰的目录>

## 纪律
- 每次 run_code 只写 <=60 行；用 fs 读写，**保留 UTF-8 BOM**（第 1 段 writeFileSync
  前置 '﻿'，后续 appendFileSync 不加）。
- 段与段之间立刻继续，不要长时间空想。**宁可分 10 小步，也不要一次想清全部再动手。**
- 不打印时间戳 / 不往 stdout 打调试输出（会破坏双跑确定性）。
- 不做 git 提交。
- 基线：<当前测试数>，**只能增加不能减少**。

## 先读（只读，5 分钟内完成）
<列出 3-5 个必须读的文件，让代理拿到真实签名/真实约束>

## 任务
<一条具体任务，含验收判据>

## 验收（必须真跑并贴输出）
<3 条以内命令>

最后回复 <=120 字：<指定要回报的 3-5 个关键数字>
```

### 1.2 为什么每条都有用（血泪对应）

| 条款 | 不写会怎样（本次实例） |
| --- | --- |
| **独占路径** | 两个代理同时改 `Simulation.cpp`，调参结果被性能修复覆盖两次 |
| **≤60 行分段写** | 一次 write 超 100 行会被截断，任务直接失败（发生 3 次） |
| **UTF-8 BOM** | 无 BOM 的中文注释在 MSVC 936 代码页触发 C4819，`/WX` 直接编译失败 |
| **不打印时间戳** | 调试输出混进 stdout，双跑确定性验收立刻失败 |
| **基线数字** | 代理悄悄删测试来让编译通过 |
| **先读真实签名** | 代理臆造 API，编译失败浪费 20 分钟 |
| **<=120 字回复** | 代理写 800 字总结，淹没关键数字 |
| **必须贴 stdout** | 代理声称"已完成"，实际从未运行 |

### 1.3 角色分工

**生成者（Generator）—— 实现 + 自测，不审自己**

```markdown
你是 <项目> 的生成者。项目根：<path>

## 你独占的路径
<...>

## 任务：<单个可验收的切片>

## 方法要求
1. 先读 <依赖文件的真实接口>，**按真实签名写，不要臆造**。
2. <具体实现要求，含关键公式/不变量>
3. **必须自己跑通验收再回复。**

## 验收（必须真跑并贴输出）
<3 条命令 + 期望结果>

## 交付
最后回复 <=120 字：改了什么、<关键数字 1/2/3>、单测与 check 状态。
不要写总结性长文。
```

**红队（Red Team）—— 新上下文，目标是证伪**

```markdown
你是 <项目> 的红队审查者。**你没有参与实现，不要维护它。目标是证明这些代码是错的。**
项目根：<path>

## 只读，绝对不改任何源文件（探针可写 build/）

## 审查范围
<文件清单>

## 判据（规格来源）
先读 <SPEC 文件路径>。**以下面这些条款为判据，不要凭直觉。**

## 重点攻击面（按优先级）
1. <不变量 1，例如能量守恒>
2. <不变量 2，例如确定性>
3. <架构红线，例如分层依赖方向>
4. <边界：NaN / 除零 / 越界 / 未初始化>
5. **是否有"声称实现了但实际没接线"的代码**（死参数、死分支）

## 已知事实（主代理实测，可作起点，但**你必须自己复核**）
<贴主代理跑出来的实际输出>

## 输出格式（每条一行，最多 14 条）
[P0/P1/P2] 文件:行 — 触发条件 — 期望/实际 — 最小修复
- P0：编译失败、UB、能量不守恒、确定性破坏、架构红线被突破
- P1：边界错误、错误被静默吞掉、验收缺失、可复现的逻辑漏洞
- P2：可维护性、命名、注释、非关键性能
能复现的必须给命令；不能复现的标 P2。**不要写总结性表扬。**
```

**关键**：红队必须**独立验证**，不能接受"主代理说已修好"。本次有 2 次主代理/生成者
声称修好、红队用探针证明并没有修好的情况（其中 1 次是主代理给的修复方案本身就是错的）。

**文档维护者 —— 只写 docs/，不碰代码**

```markdown
你是 <项目> 的文档维护者。项目根：<path>

## 你只能改这 <N> 个文件
<明确列出>
**禁止**：其他一切（尤其 src/ tests/ tools/）

## 先读
<现有文档>

## 本轮已完成的事实（主代理已验证，可直接作为证据，但要写清命令）
<逐条列出 事实 + 证据命令 + 实际输出>

## 要做的事
### A. TODO.md
- 把 <哪些> 移到「已完成」。
- **没有直接证据的留在「还没干」，不要谎报。**
### B. INDEX.md
- 每条补一行：任务 | 对应标准 | 证据（可执行命令）| 验证方式
- **禁止主观描述**（"基本完成"）。

## 输出
回复 <=90 字：新增几条、移动几条、是否写入基线快照。
```

## 第 2 部分：四文件架构（状态可恢复的关键）

### 2.1 分工

| 文件 | 职责 | 谁写 | 铁律 |
| --- | --- | --- | --- |
| `GOAL.md` | **唯一目标源**：目标、成功标准（S 编号）、阶段路线、红线、术语 | 主代理 / 用户 | 只写"要什么"，**不写状态** |
| `TODO.md` | **唯一任务状态源**：正在进行 / 已完成 / 尝试过但放弃 / 还没干 | 文档代理 | 每条带 S 编号 + 日期 + 依赖 |
| `INDEX.md` | **已完成的可执行证据**：每条映射到 S 编号 | 文档代理 | **无证据不得声称完成** |
| `DECISIONS/` | **ADR**：背景 / 选项 / 决定 / 后果 / 可逆性 | 主代理 | 推翻旧决策要写 supersedes |

### 2.2 为什么这四件有效

13 小时后我仍然能准确回答"哪些做了、证据在哪、为什么这么决定"——
因为状态从不依赖对话记忆，而是落在文件里。

**特别有效的两个设计**：

1. **S 编号是唯一的完成判据**。任何"我觉得做完了"都必须映射到 S 编号 + 可执行证据。
2. **「尝试过但放弃」分区**。记录"为什么放弃"能防止下一轮重复走弯路。

### 2.3 常见错误

| 错误 | 后果 | 修法 |
| --- | --- | --- |
| 在 GOAL.md 里写状态 | 与 TODO 冲突，两处都对不上 | GOAL 只写目标，状态全在 TODO |
| INDEX 写"基本完成" | 无法验证，等于没做 | 必须写可执行命令 + 实际输出 |
| 主代理自己改 TODO | 主代理太忙，容易漏 | 派文档代理，主代理只提供事实清单 |
| 决策不写 ADR | 下一轮重复讨论同一个选择 | 影响面大的先写 ADR 再实现 |

## 第 3 部分：门禁（Gate）设计

### 3.1 一个脚本，六项检查

```
tools\check.ps1
  [1] 依赖守卫：分层不能反向 include
  [2] 禁用守卫：不能出现 rand() / <random>
  [3] 写点守卫：只有行为层能写实体状态
  [4] 构建：编译零警告（-Werror 级别）
  [5] 单测：全过
  [6] 双跑确定性：同 seed 两次输出逐字节相等
```

**每项打印 `[PASS]`/`[FAIL]`，任一失败非零退出。**

### 3.2 门禁的价值

本次六项守卫抓到了：
- 死参数（`--policy` 解析了但没人读）
- 分层违规（探测层 include 了决策层）
- 写点逃逸（组合根直接写实体能量）
- 确定性破坏（调试输出混进 stdout）

**没有门禁的话，这些都要靠人肉审查，且大概率漏。**

### 3.3 死参数专项验收（本次最大的返工源）

同类 bug 在 R1/R4/E2 出现三轮：**CLI 参数解析了，但没有任何代码读它**。

**强制条款**（写进每个相关契约）：

> 必检：改这个参数 → 跑一次 → 输出必须变化。不变就是死参数，任务算失败。

## 第 4 部分：悬挂与失败的处置

### 4.1 如何判断代理还活着（**修正版**）

> **2026-10-31 用户更正**：曾把"没写文件"当作"已死"，误杀了两个仍在推理的代理。
> 小任务切片是对的，**错的是判活方法**。

**正确的判据（按优先级）**

1. **`list_agents` 的 status 是 `running`** —— 这是最可靠的一手信号。
   本次实测：status=running 时，代理确实还在推进，只是没落地文件。
2. **session 文件在增长** —— 辅助信号，但**刷新时机不确定**：
   一次长时间推理可能几分钟不落盘，**不增长 ≠ 死了**。
3. **沙箱里有没有新文件** —— 只能证明"已经动手"，**不能证明"没动手就是死了"**。

**结论：只有在 `status` 变成 `inactive` 之后，才认为该代理结束。**

**什么时候才考虑 interrupt**

| 情况 | 处置 |
| --- | --- |
| status=running，无文件，< 15 分钟 | **什么都不做**，它在推理 |
| status=running，无文件，15–30 分钟 | 发一条 `send_message` 问进度，**先问再杀** |
| status=running，> 30 分钟且 `send_message` 无回应 | 才 interrupt |
| status=inactive | 已结束，去读结果 |

**绝对不要**：仅凭"session 文件 N 分钟没动"就 interrupt。
那个阈值（原写 8 分钟）是错的，会误杀正在长时间推理的代理。

辅助信息（**仅作参考，不是判据**）：
```powershell
$d = Get-ChildItem $sessionsDir -Directory | Where-Object { $_.Name -like "<id-prefix>*" }
$f = Get-ChildItem $d.FullName -File
"{0} bytes, last {1}" -f ($f | Measure-Object Length -Sum).Sum, $f.LastWriteTime
```

### 4.2 处置动作

```
1. **先 `send_message` 问进度**（"你现在在哪一步？还差什么？"）—— 很多时候它只是在推理
2. 真的确认卡死才 `interrupt_agent`
3. **检查它是否已经改了文件**（避免重复劳动或半成品）
4. 判断根因：任务太大？需求模糊？模型不适合？
5. 缩小切片重派 —— 不要原样重派

**注意**：`interrupt` 之后子代理**不会留下任何收尾消息**（"left no closing message"）。
如果它其实已经写了一半文件，你会拿到一份半成品 —— 所以杀之前必须检查文件。
```

### 4.2b **PowerShell 的隐藏陷阱：Set-Location 不影响 .NET 的当前目录**

**这是本次踩到的最隐蔽的坑。**

```powershell
Set-Location 'D:\ScuStu\Q\agentsim-wt\D'
# 下面这行读的是【进程启动目录】，不是 D 沙箱！
[System.IO.File]::ReadAllText('frontend\js\main.js', [Text.Encoding]::UTF8)
Get-Content 'frontend\js\main.js'   # ← 这个是对的
```

**为什么危险**：`[System.IO.File]` / `[System.IO.File]::WriteAllText` /
`[System.IO.File]::ReadAllBytes` 用的是 **.NET 进程的当前工作目录**，
`Set-Location` 只改 PowerShell 的 provider 位置，两者不联动。

**后果（真实发生）**：我以为在读沙箱 D 的文件，实际读到了**旧项目的同名文件**，
于是得出"文件内容变了 / 结构完全不同"的错误结论，浪费了好几轮排查。

**铁律**：
1. 凡是用 `[System.IO.*]` 的地方，**一律写绝对路径**，绝不用相对路径。
2. 相对路径只配 `Get-Content` / `Set-Content` / `Test-Path` 这些 cmdlet 用。
3. 更稳的做法：整个脚本都用绝对路径，不依赖 `Set-Location`。

### 4.4 **反证式验收：证明测试真的抓得住缺陷**

代理说"修好了 + 测试通过"**不等于**测试抓住了缺陷。
可能是测试写得太松，改不改都通过。

**必做的反证实验**：
```powershell
# 1) 把修复后的代码留一份
# 2) 换回【修复前】的实现，保留【新增的测试】
# 3) 重跑 —— 新测试必须 FAIL
```

**本次实例（S16 假噪声）**：
- 用新实现：`sense_noise_is_per_candidate` PASS
- 换回旧的 `AgentSensors.cpp`（整帧共享一组噪声）：**同一测试 FAIL**

这才叫"测试抓住了缺陷"。如果换回旧代码测试仍然 PASS，那这个测试是装饰品。

**派给红队的任务里必须包含**："请你自己做这个反证实验，
如果换回旧实现测试还通过，报 P0 —— 说明测试是假的。"

### 4.5 **测试把 bug 当断言**：全绿的测试也可能是错的

**本次最深刻的教训。**

`ForageBankPolicy` 有一个 P0 缺陷：蓄能态输出"逆速度方向"，速度为零时退化为零向量，
于是核永久静止、策略形同不存在（与 StubPolicy 逐帧数值完全相同）。

**但 12 个单测全绿。** 因为其中一条断言写的是：

```cpp
// 速度为零 -> 完全静止（零向量）；绝不吃食物方向。
CHECK_NEAR(a.dirX, 0.0, 1e-12);
```

**这条断言字面固化了缺陷。** 测试作者把"当前实现的行为"当成了"应该的行为"。
于是 bug 被测试保护起来，红队和门禁都抓不到。

**怎么防**：
1. 写断言时问自己：**"这是规格要求的，还是实现碰巧这样的？"**
   规格里没有的"恰好行为"不要写成 CHECK。
2. 更要紧的是**纵向集成测试**：单测都过，但策略上线后与另一个策略输出完全相同 —— 只有跑
   真实 CLI 才看得见。**每个新策略必须有一条"与其它策略输出互异"的集成测试。**
3. 出现"两个策略数值相同"时，不要假设是巧合，直接查是不是有一方根本没起作用。

**同类信号（都真实发生过）**：
- 死参数：`--agent-mode 1` 加了等于没加
- 假噪声：三个候选共享同一组随机偏移，排序不受影响
- 死代码：`colonyCap` 实现了但不上生产路径

**共同点：单元层面全绿，集成层面才暴露。所以门禁必须有"参数/策略真的起作用"这一类检查。**

### 4.6 **比较输出时必须剥掉元信息**

判断"两个配置输出是否相同"，直接 `-eq` 比较整行是错的：

```powershell
# 错：末尾的 policy=stub / policy=foragebank 不同，永远判 differ
$a -eq $b
# 对：先剥掉会随配置名变化的部分
($a -replace ' policy=\w+','') -ceq ($b -replace ' policy=\w+','')
```

我因此把"foragebank 与 stub 完全相同"误判为"正常"，浪费了一轮排查。

### 4.3 失败分类与对策

| 症状 | 根因 | 对策 |
| --- | --- | --- |
| `terminated`，session 无增长 | 悬挂（"想太久"） | 切片更小；`reasoning_effort` 用 low |
| `HTTP 502 / 429` | 上游不稳 / 并发超限 | 等一个周期再派；降并发 |
| 完成后文件没变 | 任务太模糊，代理在"思考" | 契约里给**逐字可执行**的步骤 |
| 反复改不对同一个数学问题 | 模型推不动 | **主代理直接接手**（本次 3 次） |

### 4.4 一个重要的判断

**越精确的逻辑/数学修复，越不该交给子代理。**
本次"reproduce 账目恒等式"和"trustFood 变负"两处，是主代理自己推导公式后直接改的，
派出去的代理反而推了 30 分钟无产出。

## 第 5 部分：自动唤醒（定时任务）的正确用法

### 5.1 实测行为

- 定时提醒**不会打断正在跑的回合**，要等当前回合结束才送达（实测延迟 4 分钟）。
- 到点后条目自动从列表消失（投递成功）。

### 5.2 频率选择

**本次的教训**：一开始设 20 分钟一次，结果提醒大量堆积（我干一轮要 20-60 分钟，
提醒来得比我推进得快），反而成为噪音。

**建议**：
- 主循环用 **2-4 小时一次**，作为"看门狗 + 恢复点"
- 不要用提醒做密集驱动——连续性应该由任务队列自己保证
- 提醒的 prompt 要写**具体动作**（读哪个文件、跑哪条命令），不要写"继续推进"

### 5.3 提醒 prompt 模板

```
[看门狗] 读 <项目>/docs/WORKFLOW.md 的「循环」一节，执行一次：
1. list_agents 收集状态
2. 自己跑门禁（<具体命令>）
3. 若上一波已完成，派红队审 diff
4. 按红队 P0/P1 派生成者修
5. 派文档代理更新 TODO/INDEX
6. 派下一个任务
铁律：主代理不写实现代码；每账号并发 <= N；同一时刻同一文件只允许 1 个代理写。
```

## 第 6 部分：一天的循环模板

```
[循环开始]
 1. 收状态：list_agents；已完成的读其报告
 2. 自己跑门禁（不委托）：build / unit / 关键验收命令
 3. 门禁红 → 先修门禁，不派新活
 4. 门禁绿 → 派红队审最近一批 diff
 5. 红队出 P0/P1 → 派生成者修（切片 <=8 min）
 6. 红队无 P0/P1 → 派文档代理更新四文件
 7. 派下一个任务（保持 4 槽打满）
 8. 回到 1
[循环结束条件]
 · 全部 S 编号有证据
 · 或用户要求交付
```

## 第 7 部分：一页检查清单

派活前：
- [ ] 独占路径写清了吗？
- [ ] 禁止路径写清了吗？
- [ ] 给了真实签名/真实约束吗？（不是"你应该知道"）
- [ ] 验收命令 <=3 条吗？
- [ ] 能在 8 分钟内做完吗？
- [ ] 要求回报的关键数字 <=5 个吗？

红队前：
- [ ] 是新上下文吗？
- [ ] 给了规格文件路径吗？
- [ ] 明确"目标是证伪"了吗？
- [ ] 要求独立复核而不是接受现成结论了吗？

收尾时：
- [ ] 每条完成项都有可执行证据吗？
- [ ] 没完成/放弃的写原因了吗？
- [ ] 基线数字更新了吗？
- [ ] 有"名不副实"的地方需要记录吗？
```
