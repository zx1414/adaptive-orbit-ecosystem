# ADR-002 食物再生与账本归属

- 编号：ADR-002
- 状态：已接受（Accepted）
- 日期：2026-10-31
- 关联：GOAL.md S3（能量账本零和）、R2.3（生产者基础版）、§6 能量红线；TODO.md T02/T06/T07/T09；ADR-001
- supersedes：无；被 supersede：无

## 背景

初版最小闭环跑通后，主代理验收暴露两个缺陷（均已于 2026-10-31 修复并复测）：

- **D1（P0，审计失败）**：仿真构造时只对核能量做了 `injectInitial`，食物池能量从未入账——
  零和恒等式 `injected - dissipated == Σ实体能量` 自第一 tick 起就差一份食物总能量；
  同时进食侧既 `injectPrimary` 又 `transfer` 双记食物能量；死亡时的负能量残差又被
  `dissipate(0)` 掩盖。根因：食物能量的**账本归属**（算谁的、谁注入、进食走哪条路）从未定义。
- **D2（P1，生态瞬灭）**：`eatRadius=25` 且每核每 tick 限食 4 个 ⇒ 12 核理论上每 tick 吞 48 个食物，
  又无任何再生机制，初始食物池数 tick 内被吃光，生态必然瞬灭。

修复过程中固化了三项低可逆决策：账本归属（决定①）、再生与唯一初级注入（决定②）、限额支出（决定③）。
修复后主代理复测：`build\agentsim.exe --no-render --ticks 5/2000/20000 --seed 42 --audit`
均 `audit=ok`[exit 0]；`tools\check.ps1` 五项全 PASS；同 seed 双跑逐字节一致。

## 决定 ① 食物池固定 id=0（kFoodPoolId），进食是纯 transfer 零和

### 选项

- A. 食物能量在吃下时直接对核 `injectPrimary`：不需要池实体，账面简单，但注入总额随进食漂移。
- B. 食物池作为固定实体 id=0（`kFoodPoolId`）：食物能量在初始生成/再生时以池为主体一级注入；
  进食只做 `transfer(kFoodPoolId → 核, got)` 的零和搬运。
- C. 每个食物个体是独立账本实体，各自注入/转移：账目最细但注入/流量爆炸，初版过重。

### 决定

采用 B。`src/behavior/AgentBehavior.h:20`：`constexpr EntityId kFoodPoolId = 0;`；
进食路径 `src/behavior/AgentBehavior.cpp:77-89`：`consumeFood` 返回实际吃到能量 →
核能量增加 → 仅 `ledger.transfer(kFoodPoolId, n.id, got)`，绝不重复 `injectPrimary`。

### 后果

- 好处：账本恒等式自第一 tick 起严格成立（食物能量已在初始注入计入）；进食是流量搬运，
  injected/dissipated 总额稳定，双记类 bug 会被审计立即抓住（D1 即例证）。
- 代价：实体 id 空间永久保留 id=0；"池作为一级注入主体"的语义与审计公式绑定，改动需重定基线。
- 风险：后续贡献者忘约定在进食侧再注入即复现 D1——由零和审计 + 单测 ledger_transfer_zero_sum 约束。

### 可逆性

中。`kFoodPoolId` 是单一常量，机械替换容易；但"池=一级注入主体"已是审计基线的一部分，
Phase 2 前不建议动。

## 决定 ② 食物每 tick 定额再生（kFoodRegrowPerTick），injectPrimary 为唯一初级注入

### 选项

- A. 不再生：生态必然瞬灭（D2 实证），排除。
- B. 每 tick 定额再生：`env_.regrowFood(rng_, kFoodRegrowPerTick=2)`，再生能量经
  `ledger_.injectPrimary(kFoodPoolId, regrown)` 入账。
- C. 密度相关的 logistic 再生（承载量曲线）：更真实但初版过重。

### 决定

采用 B。`src/sim/Simulation.cpp:15-16` 定义 `kFoodRegrowPerTick = 2`；
`Simulation.cpp:68-72` 每 tick 调 `regrowFood` 并一级注入。食物能量的初级注入**只有两处**：
构造时 `injectPrimary(kFoodPoolId, env_.totalFoodEnergy())`（Simulation.cpp:19-20，D1 修复）
与每 tick 再生注入——均入 kFoodPoolId 账户；其余任何代码不得对食物能量做 `injectPrimary`。

### 后果

- 好处：生产者（蓝细菌）基础版成立；再生走自传 PCG32，确定性不受影响；注入源唯一，审计可溯源。
- 代价：定额再生非密度相关；实测食物 53（tick 5）→ 47（tick 2000）→ 34（tick 20000），
  池缓慢净消耗，再生与进食接近平衡，参数需后续标定；再生受 `food.max` 上限约束并复用耗尽槽位。
- 风险：进食参数（eatRadius=14、每 tick 限食 2）与再生速率必须联合平衡，否则复发瞬灭或食物膨胀
  （D2 教训；相关参数在 `BehaviorParams` 注释中标注"D2 调参"）。

### 可逆性

高。再生速率是常量，换 logistic（选项 C）只改 `Simulation::step` 与 `AgentEnvironment::regrowFood`；
"唯一初级注入"是架构约定，一经接受不得随意违反（违反 = 复现 D1）。

## 决定 ③ 耗能采用限额支出（spend = min(需求, 余额)）

### 选项

- A. 全额支出允许实体能量为负，死亡清算时补账：恒等式需引入负残差约定。
- B. 限额支出：`spend = min(需求, 余额)`，实体能量永不为负；死亡仅对正余额 dissipate。
- C. 能量 ≤ 0 立即死亡、债务直接勾销：A 的变体，同样需要负残差约定。

### 决定

采用 B。`src/behavior/AgentBehavior.cpp`：移动耗能（59-63 行）与呼吸耗能（67-75 行）均为
`const double spend = 需求 < n.energy ? 需求 : n.energy;`，仅对实际扣除额 `ledger.dissipate`；
死亡分支（约 121-140 行）只在正余额时 `dissipate("death", left)`，球储能随核死亡全额耗散回收。

### 后果

- 好处：实体能量恒非负 ⇒ "实体扣减 == 账面耗散"逐位成立，无需负残差修复逻辑，
  D1 的"负残差被 dissipate(0) 掩盖"从结构上不再可能出现；审计只需浮点容差。
- 代价：低余额核退化为"半饥饿滑行"而非负债速死，饥饿压力弱于理想模型，死亡时点右移。
- 风险：需求超出余额的部分直接消失（不入账）——这是设计意图（未支付的需求不构成流量），
  但评审须知晓：`dissipate` 只与实际扣除额成对出现。

### 可逆性

中高。三处调用点局部化；若后续要更强饥饿压力（选项 A/C），需给审计加负残差约定并重跑全部审计基线。
